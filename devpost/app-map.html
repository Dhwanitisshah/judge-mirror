Judge Mirror: app map

A take-home guide to the finished code. Source commit 6d444c4. This is a snapshot: the code will drift, so check git log if something doesn't match.

What it is

You paste a hackathon's judging criteria and your submission, and Judge Mirror marks up your own text in red pen: a score per criterion, the exact sentences that earned it, and one fix. The point of the build was one idea: the model's answer is a claim, and code is the judge of that claim. Every quote the model returns must be found in your text before you ever see it.

The screens

src/app/page.tsx holds all state in one reducer (src/lib/state.ts) and switches between input, chips, marking, results and error.

The two routes

src/app/api/review and src/app/api/parse-criteria. Only these talk to Gemini, so the key never reaches the browser.

The judge

src/lib/verify.ts (with normalize.ts) checks every quote and every injection flag against your real text. Pure functions, no network.

The red pen

PaperPage.tsx draws only what the server verified, using hand-drawn SVG strokes from src/lib/handdrawn.ts.

One action, end to end: "Review my submission"

  1. The browser sends your text. src/app/page.tsx → runReview(), POST /api/review
  2. The route checks the size limits and asks for a review. src/app/api/review/route.ts → POST, reviewWithModel()
  3. Gemini is asked for structured JSON. Busy or slow models are skipped (503, 429, 504, timeout), one attempt each, 25 s caps. A reply that breaks the contract gets exactly one retry, with the problem attached. src/lib/llm.ts → generateWithFallback(), REVIEW_MODELS, PER_MODEL_CAP_MS  |  prompt in src/lib/prompts.ts
  4. Trust boundary. Zod and the rules a schema can't say (right names, no evidence means score 1 or 2). Then every quote and flag is searched for in your text, and what isn't found is dropped. code is the judge src/lib/review.ts → parseModelOutput(), buildReviewResponse()  |  src/lib/verify.ts → verifyCriterion(), verifyFlag()
  5. Code derives what the model must not decide: an all-fabricated criterion gets no score; with no transcript, Presentation is capped at 3. src/lib/verify.ts → deriveState()  |  src/lib/review.ts (the null score and the cap), isPresentation() in src/lib/notes.ts
  6. The browser draws only verified marks, by character position, and shows which model answered. src/components/PaperPage.tsx, ResultsScreen.tsx → "Marked by …"

A route through the code (reference route, 3 stops)

This is a suggested route. It was not walked through interactively during the build. Open the files in your editor and search for the symbol.

1. Where the model's reply is accepted or rejected. src/lib/llm.ts, search generateWithFallback. Follow opts.validate(readJson(result)): a bad reply triggers retryNote() once; a second bad reply becomes bad_output. A busy or slow model never reaches this check; it is skipped.

2. The gate. src/lib/verify.ts, search verifyQuote. A quote is cleaned (no ellipsis, 12 to 300 characters), matched case-sensitively against your text after smoothing whitespace, curly quotes and dashes (normalizeWithMap remembers where every character came from), and returned as positions in your original text. No match, no mark.

3. What happens after the gate. src/lib/review.ts, search buildReviewResponse. See how an unverifiable card has its score set to null and its verdict blanked, so fabricated text never leaves the server, and where the Presentation cap lowers a score.

A practice to reuse: make code the judge of the model's claims

The decision. Every quote the model returns as evidence must be found in the user's real text, or it is dropped (src/lib/verify.ts). The model never gets to say "trust me".

The evidence it worked, and where it stopped.

  • src/lib/review.test.ts runs the fixture through the real pipeline and checks that no fabricated quote, flag, verdict or fix appears anywhere in the JSON sent to the browser.
  • src/lib/verify.test.ts was checked by breaking verify.ts on purpose five ways (no ellipsis rule, off-by-one minimum, no source fallback, wrong end offset, case-insensitive match). Each one made the tests fail. A test you have never seen fail proves little.
  • Across the real runs, 0 quotes were dropped: the models quoted faithfully here, so the gate had little to catch live. The Experiment Log in devpost/spec.md has the numbers.
  • Verification has a limit. The strong submission scored Presentation 5 from its text alone. Its quotes were real, so the gate passed, yet the score was too generous for a criterion about a video. A check on quotes can't catch an over-generous score. The response was a second code rule (cap at 3 with no transcript, review.ts), tested in review.test.ts.

How to reuse it on another project.

  1. List what the model claims: facts, quotes, numbers, scores.
  2. For each claim ask: can code check this against ground truth? If yes, check it and drop what fails, and never display the unchecked version.
  3. If code can't check it, bound it (a range, a cap, a derived null) and say on screen that it was bounded.
  4. Prove each check can fail: break it on purpose and watch a test go red.

Run it again

npm install
copy .env.example .env.local        # then add GEMINI_API_KEY (never commit .env.local)
npm run dev                         # http://localhost:3000, mock mode when LLM_MOCK=1
npm test                            # 148 tests, no network
npm run typecheck                   # generates Next's types, then runs tsc

# a real review, in a second terminal (PowerShell):
npm run build
$env:LLM_MOCK="0"; npx next start -p 3100       # http://localhost:3100
